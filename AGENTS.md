# AGENTS.md

For coding agents working in this repository. The [README](README.md) is the
manual; this is what an agent needs to know before it changes anything, and
would not learn from the file it happens to be editing.

## What this is

A daemon for a Raspberry Pi with a Waveshare 2.9" e-paper panel (V2), written
in Zig 0.17.0. It takes readings from the machine, draws a dashboard, puts it
on the panel over SPI and GPIO, publishes the readings over MQTT, serves a
preview and a small HTTP API, and shows notices sent to it.

It runs on the Pi and nowhere else: the first thing it does is open the GPIO
chip and the SPI device. It takes no command-line arguments, so **running the
binary with any, `--version` included, starts a second daemon.** Do not run it
to find something out.

## Before calling a change done

These are what CI runs. All four, every time.

```bash
zig build test --summary all
zig build test -Doptimize=safe --summary all
zig build check
zig fmt --check src build.zig
```

- `check` type-checks `main.zig` for every target a release is built for,
  32-bit ARMv6 among them. The tests cannot stand in for it: they build for
  one architecture, and `main.zig` is not part of them.
- If you touched the layout or the renderer, run `zig build golden`. It must
  leave `src/testdata/golden_main.bin` unchanged unless changing what the
  panel shows was the point; then review the difference in the simulator.
- `zig build sim` and `zig build sim-web` run until stopped. Do not put them
  in a script that waits for them.

**A green run on macOS says nothing about Linux.** The notice pipe, the HTTP
server and a few others are tested on Linux only, and sockets do not behave
alike on the two. CI is Linux. From another host, cross-compile the tests,
which fails at running them and prints the binary's path after
`failed command:`, and run that on a Linux machine from an empty directory
(the fixtures are written under the working directory):

```bash
zig build test -Dtarget=aarch64-linux-musl -Dcpu=baseline
```

## Where things go

- `src/main.zig` is wiring: read the settings, put the parts together, run the
  loop. It is Linux-only and under no test, so no logic goes there.
- `src/app.zig` holds the daemon's tasks, generic over the panel's transport;
  `src/app_logic.zig` holds what they decide, free of I/O. Both are tested.
- `src/config.zig`: every setting is read once, through `Env`, into a value
  that `main` hands on. Nothing else reads the environment and there are no
  globals. A new setting is a field of `Config` with its default, a line in
  `fromEnv`, a row in the README's tables and a line in the changelog.
- `src/reading.zig`: a reading is current, stale or unavailable, and the
  panel, the API and MQTT all say which. A new reading goes through
  `Reading(T)`. Its field in `api.Status` must also be in `api.Stale` or in
  `api.never_stale`; the build fails otherwise.
- `src/sysroot.zig`: procfs and sysfs are read through a `Root`, which is `/`
  on a machine and a tree of fixtures (`Fixture`) under test. Parsing is in
  `src/parse.zig`, free of I/O.
- `src/display_config.zig` says where things go on the panel and is imported
  as `layout`; `src/display_renderer.zig` says what is drawn there;
  `src/panel.zig` and `src/waveshare_epd/` put it on the glass, and
  `fake_transport.zig` is the recorder that stands in for it.
- `src/ioctl.zig` derives ioctl request numbers from the types they take.
  Whoever derives one pins it in a test against the kernel's value.
- `src/font_data.zig` is generated by `tools/fontgen.c`. Do not edit it.

## How things are done here

1. **Keep a change to what was asked.** Before one that touches many files, a
   rename or a move above all, say what it will touch and wait for an answer.
   No clean-ups on the way past.
2. **Names** follow the Zig style guide: types in `TitleCase`, functions in
   `camelCase`, everything else in `snake_case`, enum fields and constants
   included. A name established elsewhere keeps its spelling: the ioctl
   request numbers are named as the kernel's headers name them. Do not rename
   what mirrors an outside specification.
3. **Nothing may hold up the main loop.** Connecting, sending and reading are
   bounded in time or in bytes, and a name is looked up off the loop. A new
   call that can block needs its bound.
4. **Nothing is passed over in silence.** A reading that could not be taken is
   not reported as current. A setting that cannot be used is turned down in
   the log, with what is used instead.
5. **Secrets stay out of the log and out of child processes.** The value of a
   setting that may be one (`MQTT_PASSWORD`, `WEB_API_TOKEN`) is never logged,
   and commands the daemon runs get the environment from
   `config.childEnvironment`. On a device, do not print the environment file.
6. **Tests are named by what they hold true**, as a sentence: "a reading that
   stops answering is reported with its last value and its age". New
   behaviour comes with one. What talks to hardware goes behind the seams
   above, so that it can have one.
7. **Comments say why**, in sentences, as densely as the file around them.
8. **What a user can notice goes in the docs**: `CHANGELOG.md` under
   Unreleased, the README's configuration tables, and `docs/openapi.yaml` for
   the API.

## Git

- A branch is named for the type of change and what it does:
  `fix/wifi-signal-interface`, `feat/mqtt-tables`, `refactor/…`, `test/…`,
  `docs/…`, `chore/…`. Never for a tool or a session.
- A commit is `type: a sentence saying what is now true`, with a body that
  says why and how it was checked. One change to a commit, and every commit
  builds and passes the tests.
- No attribution to a tool or an assistant, anywhere: no `Co-Authored-By` for
  one, no "generated with" line, in a commit, a pull request, the code or the
  docs.
- **Passing tests do not finish a change that reaches the panel, the GPIO or
  SPI lines, the broker or the service.** The tests do not show the glass. It
  has to run on a device first: do not commit such a change, or offer to,
  until the maintainer has seen it work there.
- Do not push, tag or open a pull request unless asked.
- Other worktrees may hold work that is not committed, and one of them may be
  what a device is running. Look (`git worktree list`) before a wide change,
  and leave them alone.
